# اصلاح و تشخیص تحلیل رزومه در محیط محلی

تاریخ: ۲۰۲۶/۱۱/۱۵. این بررسی فقط روی لپ‌تاپ و Docker محلی انجام شد؛ سرور، انتشار و مدل آموزش‌دیده تغییر نکردند.

## علت‌های تأییدشده

- Redis یک رزومهٔ منتظر و صفر Worker ثبت‌شده داشت؛ بنابراین تحلیل شروع نشده بود.
- API محلی روی `multi_agent` بود و نشانی مدل نداشت. شباهت ظاهری مشکل محلی و سرور، اثبات علت یکسان نبود.
- تصویر پیش‌نمایش `langgraph` و `tokenizers` نداشت. مسیر مدل بی‌دلیل پیش از اجرا LangGraph را وارد می‌کرد؛ با جداسازی مسیر، Worker دیگر به آن نیاز ندارد. tokenizer فقط در تصویر موجود درگاه استفاده می‌شود؛ نصب جدیدی انجام نشد.
- خطاهای مسیر قبلی با بازگشت عادی پنهان می‌شدند و RQ کار را موفق می‌دید. ذخیرهٔ متن نیز به موفقیت تحلیل وابسته بود.

## رفتار اصلاح‌شده

`app/tasks/resume_model.py` اجرای اختصاصی مدل را انجام می‌دهد. درخواست، رزومه، کارجو و سازمان باید منطبق باشند. قفل کوتاه ردیف برای تصاحب تلاش و هر ذخیره استفاده می‌شود؛ تراکنش هنگام OCR یا درخواست شبکه باز نمی‌ماند. شناسهٔ تلاش جلوی نوشتن نتیجهٔ تلاش قدیمی را می‌گیرد. هش SHA256 فایل و نسخهٔ cache تعیین می‌کنند که متن و دادهٔ پارس‌شده قابل استفادهٔ مجدد هستند یا خیر. با تغییر فایل، تحلیل و امتیاز نسخهٔ قبلی نیز پاک می‌شوند.

متن بلافاصله پس از استخراج و دادهٔ ساختاریافته پس از پارس، در تراکنش‌های جدا و با رمزنگاری موجود ذخیره می‌شوند. تحلیل و امتیاز در یک commit نهایی ذخیره می‌شوند؛ وضعیت استخدام تغییر نمی‌کند. وضعیت عملیاتی در ستون nullable جدید `resumes.processing_state` ثبت می‌شود. migration `f19b3a47d682` با تأیید کاربر فقط روی `ats_preview` محلی اجرا شد.

خطاهای شبکه/ظرفیت با کد ثابت به RQ برمی‌گردند. سیاست برنامه همان دو retry با فاصله‌های ۶۰ و ۳۰۰ ثانیه و مهلت کار ۳۰۰ ثانیه است. فایل ناخوانا، خروجی ناقص/نامعتبر، ورودی بزرگ‌تر از ظرفیت و خطای پیکربندی، موفقیت محسوب نمی‌شوند و بی‌نهایت تکرار نمی‌شوند. خطای اصلی یا بدنهٔ حساس آن وارد استثنای صف نمی‌شود. کدهای ثابت درگاه حفظ می‌شوند؛ مثلاً `context_limit_exceeded` با timeout اشتباه گرفته نمی‌شود. شکست enqueue نیز پاسخ ۵۰۳ و وضعیت `queue_unavailable` دارد؛ فایل ذخیره‌شده از بین نمی‌رود.

Worker لینوکسی RQ در Docker همراه زمان‌بند داخلی اجرا می‌شود؛ healthcheck ثبت واقعی آن را بررسی می‌کند. مسیر سازگار ویندوز حفظ شده، اما برای retry زمان‌دار باید از محیط Docker استفاده کرد. شرح کار و extra آرگومان‌های رزومه در لاگ Worker حذف شده‌اند. در توقف ناگهانی، lease پردازش پس از ۳۶۰ ثانیه منقضی می‌شود و API به‌جای نمایش دائمی «در حال پردازش»، `processing_expired` نشان می‌دهد؛ این انقضا به‌تنهایی به معنی موفقیت یا retry نامحدود نیست.

API وضعیت `GET /api/v1/resumes/{id}/processing` فقط برای صاحب رزومه یا HR/Admin همان سازمان قابل دسترسی است. در پروندهٔ HR و رهگیر کارجو نیز فقط وضعیت عمومی، مرحله، شمارهٔ تلاش و کد خطای امن منتشر می‌شود؛ شناسهٔ تلاش، هش فایل، Redis args و traceback منتشر نمی‌شوند. polling هر پنج ثانیه، در پس‌زمینه غیرفعال، با سقف ۱۲۰ دریافت و توقف روی خطا یا وضعیت نهایی است. وضعیت استخدام از وضعیت تحلیل جداست.

## اجرای فعلی و راه‌اندازی مجدد

فایل‌های نگهداری‌شده: `dev/compose.local.yml`، `dev/compose.resume-local.yml`، `dev/resume-local.cjs` و `inference/compose.diagnosis.yml`. volumeهای قبلی دیتابیس، Redis و رسانه حفظ شده‌اند. رازها در `secrets/editorial-local.json` و `secrets/editorial-docker.env` می‌مانند. کلید خصوصی موجود `secrets/inference/worker.pem` فقط برای Worker مانت می‌شود. تغییر یا ساخت کلید خودکار انجام نمی‌شود.

از ریشهٔ پروژه:

```powershell
node dev/resume-local.cjs up
node dev/resume-local.cjs status
```

دستور اول فقط سرویس‌های ATS محلی را مدیریت می‌کند، بدون build یا pull. Worker پس از آماده‌بودن مدل شروع می‌شود. اجرای دوباره، سرویس موازی ایجاد نمی‌کند. دستور `stop` فقط API، Worker و مدل همین محیط را متوقف می‌کند؛ دیتابیس/Redis و سرویس‌های پروژه‌های دیگر باقی می‌مانند. این محیط فعلی به تصویرهای موجود `ats-editorial-api:local` و `ats-inference-api:task4`، فایل‌های راز محلی، Docker با GPU و artifactهای قبلی وابسته است؛ برای نصب روی رایانهٔ تازه باید این پیش‌نیازها جداگانه تأمین شوند. migration روی محیط تازه باید پیش از شروع Worker اعمال شود؛ اسکریپت خودکار ساختار دیتابیس را تغییر نمی‌دهد.

- رابط موجود Vite: `http://localhost:5173`
- API: `http://localhost:8000/api/v1`
- آمادگی درگاه: `http://localhost:8081/ready`
- مسیر: `RESUME_PIPELINE=model`؛ در Docker نشانی درگاه `http://host.docker.internal:8081` است. fallback به سرویس خارجی یا مسیر چندعاملی انجام نمی‌شود.

## نتیجهٔ اندازه‌گیری‌شدهٔ رزومهٔ صف‌شده

همان رزومهٔ موجود، در تلاش اول با موفقیت تحلیل شد. متن استخراج‌شده، دادهٔ پارس‌شده و تحلیل در دیتابیس ذخیره شدند. برای این درخواست، retry یا ارسال دوباره ساخته نشد.

| مرحله | زمان |
| --- | ---: |
| خواندن فایل | ۱۳٫۷۵ میلی‌ثانیه |
| استخراج متن | ۱۹٫۴۸ میلی‌ثانیه |
| پارس اولیه | ۱۷۶۳٫۱۷ میلی‌ثانیه |
| کل درخواست مدل از دید Worker | ۳۲۹۹٫۳۹ میلی‌ثانیه |
| آماده‌سازی prompt و tokenization در درگاه | ۴٫۴۴ میلی‌ثانیه |
| درخواست موتور از دید درگاه | ۳۱۳۴٫۹۹ میلی‌ثانیه |
| ارزیابی prompt در موتور | ۷۱۳٫۵۳ میلی‌ثانیه |
| تولید خروجی در موتور | ۲۴۰۶٫۸۴ میلی‌ثانیه |
| اعتبارسنجی پاسخ در درگاه | ۰٫۵۷ میلی‌ثانیه |
| نگاشت تحلیل | ۹٫۷۷ میلی‌ثانیه |
| commit نهایی نتیجه | ۵۷٫۶۸ میلی‌ثانیه |

ورودی ۱۲۵۷ و خروجی ۱۷۲ توکن بود؛ ظرفیت context برابر ۲۰۴۸ و سقف خروجی ۶۴۰ باقی ماند. زمان‌های داخلی موتور زیرمجموعهٔ درخواست مدل‌اند و نباید دوباره جمع شوند. جمع مراحل اصلی ثبت‌شده حدود ۵٫۱۶ ثانیه است؛ زمان انتظار قبلی صف و تمام تراکنش‌های میانی را شامل نمی‌شود و زمان کل HTTP آپلود نیست. این اولین درخواست کاربردی پس از راه‌اندازی موتور بود؛ warmup داخلی موتور از تنظیم قبلی حفظ شد. درخواست‌های ساختگی بعدی روی موتور گرم اجرا شدند و مقایسهٔ همسان سرد/گرم روی رزومهٔ کاربر انجام نشد. API غیر streaming است؛ زمان اولین توکن قابل مشاهده نبود و گزارش نشده است.

GPU: RTX 4050 Laptop با ۶۱۴۱ MiB. نمونهٔ پایان بررسی: حدود ۲۹۸۱ MiB مصرف GPU، حدود ۵۰ MiB RAM برای Worker در حالت بیکار، ۵۰۰ MiB برای موتور و ۱۱۶ MiB برای درگاه. این اعداد نمونهٔ لحظه‌ای‌اند، نه peak زمان درخواست. شمارندهٔ OOM کانتینر Worker صفر بود. نمونهٔ سیستم حدود ۴۹۵۳ MiB RAM آزاد و ۱۳۵۷ MiB `FreeVirtualMemory` داشت؛ آزمون طولانی فشار حافظه انجام نشد. فایل عددی `resource-snapshot.json` شواهد کانتینرها را نگه می‌دارد.

مدل همان `models/ats-gguf/ats-q4_k_m.gguf` با اندازهٔ ۱٬۹۲۹٬۹۰۲٬۵۹۲ بایت و SHA256 زیر است:

```text
27a6e84cb2e5124cb3b62d733c01614b98fb476aab497bbca3e000d88192ebda
```

tokenizer موجود و `models/grammar/hybrid-v2.json` استفاده شدند؛ تطبیق fingerprint و اعتبارسنجی خروجی حفظ شد. مدل با دیتاست ساختگی آموزش دیده است؛ موفقیت فنی این اجرا اثبات کیفیت ATS در دنیای واقعی نیست.

در Worker، نسخه‌های موجود RQ برابر ۱٫۱۶٫۲، Redis client برابر ۵٫۰٫۸، spaCy برابر ۳٫۸٫۱۶، HTTPX برابر ۰٫۲۸٫۱، Pydantic برابر ۲٫۹٫۲ و SQLAlchemy برابر ۲٫۰٫۳۵ بررسی شدند. Tesseract و زبان‌های `eng`، `fas` و `osd` موجودند؛ تنظیم `fas+eng` قابل استفاده است. رزومهٔ صف‌شده از لایهٔ متنی استخراج شد؛ OCR تصویری روی رزومهٔ کاربر اجرا نشد. زمان‌های داخلی از headerهای عددی مجاز منتقل می‌شوند؛ بدنه و schema عمومی `ats-inference-v1` برای سازگاری کلاینت‌های strict قبلی ثابت مانده است.

## شواهد و بررسی دستی

شواهد بدون متن رزومه در مسیر ignored `training/reports/resume-repair/` قرار دارند:

- `queued-resume-result.json`: وضعیت و اندازه‌گیری‌های عددی؛ بدون شناسه یا محتوای رزومه.
- `rq-check-result.log`: آزمون واقعی RQ با صف و سازمان ساختگی جدا؛ دو retry، شکست نهایی، حفظ متن، استفادهٔ مجدد از مراحل، موفقیت مدل واقعی و فایل خراب. فقط فاصلهٔ retry آزمون ایزوله یک ثانیه بود؛ سیاست برنامه تغییر نکرد. داده‌ها و صف همان آزمون پاک شدند.
- `backend-tests.log`: خروجی تست‌های مرتبط بک‌اند.
- `resource-snapshot.json`: نمونهٔ مصرف منابع پس از بررسی.
- `synthetic-status-375.png` و `synthetic-status-1440.png`: نمایش هر پنج وضعیت با fixture مشخصاً ساختگی؛ بدون سرریز افقی.
- `rendered-status-check.json`: نتیجهٔ مرورگر واقعی Edge. این تصاویر بررسی مستقل مؤلفهٔ وضعیت‌اند؛ تصویر پروندهٔ واقعی کاربر تهیه نشده است.

دستورهای بررسی:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/unit/test_model_inference.py tests/unit/test_resume_model.py tests/unit/test_queue_retry.py tests/integration/test_tenant_isolation.py tests/integration/test_resume_processing_worker.py tests/integration/test_candidates_api.py tests/integration/test_applications_api.py -q
# تست‌های integration با TEST_DATABASE_URL محلی و TEST_DB_REQUIRED=1 اجرا شدند؛ دیتابیس تست موقت است.
cd frontend
npm run build
npm test -- --runInBand
node resume-status-check.cjs
```

نتیجهٔ اجرای تجمیعی بک‌اند: ۸۶ تست پاس شدند. پس از حفظ قرارداد strict، انتقال telemetry به header و افزودن پوشش پاک‌سازی خطای پیش از تصاحب رکورد، ۵۸ تست واحد مربوط به مدل، lifecycle و صف دوباره پاس شدند. در فرانت‌اند `npm run build` موفق بود و `npm test -- --runInBand` با ۵۲ تست در ۱۳ suite پاس شد. Black و Flake8 فایل‌های تغییرکرده موفق بودند. هشدارهای deprecation کتابخانه‌ها و هشدارهای موجود `act` در تست کانبان باقی‌اند؛ failure تست باقی نماند. بررسی مرورگر نیز در هر دو عرض، چهار پیام status و یک alert و بدون سرریز افقی ثبت کرد.

در رابط محلی صفحه را تازه کنید و پروندهٔ همان درخواست را باز کنید: وضعیت «تحلیل ذخیره شد»، متن و تحلیل باید قابل مشاهده باشند. در پنل کارجو، تب رهگیری نیز وضعیت تحلیل را جدا از مرحلهٔ استخدام نشان می‌دهد. برای آزمون بعدی از فایل ساختگی استفاده کنید؛ پس از آپلود، درخواست ۲۰۲ صرفاً پذیرش در صف است و موفقیت تحلیل با وضعیت `succeeded` مشخص می‌شود. هنگام خطا، کد پیگیری و متن استخراج‌شدهٔ حفظ‌شده در پرونده نمایش داده می‌شوند. برای دیدن خطای ساختگی نیازی به خاموش‌کردن مدل فعال نیست؛ تصاویر fixture و تست مستقل وضعیت موجودند.

## محدودیت و ادامهٔ پیشنهادی

نتیجهٔ لوکال به سرور CPU تعمیم داده نمی‌شود. مهلت‌ها، منابع و کیفیت/ساختار خروجی برای پاس‌کردن آزمون تضعیف نشدند. prompt بزرگ‌تر از ظرفیت، خطای قطعی دارد و متن بی‌صدا بریده نمی‌شود. افزایش ظرفیت، بخش‌بندی رزومه یا کاهش زمان تولید باید جداگانه با بررسی اثر کیفیت تصمیم‌گیری شود؛ در این کار اعمال نشد. اصلاح lifecycle اختصاصی مسیر `model` است؛ رفتار best-effort قدیمی `linear` و `multi_agent` بازطراحی نشده است. هیچ push یا تغییر پروداکشن انجام نشده است.
