# معماری چندمستاجری (Multi-Tenancy) در سطح پایگاه داده

هر سازمان مشتری (ردیف جدول `companies`) یک **Tenant** است. داده‌ی عملیاتی هر سازمان با ستون `tenant_id` جدا می‌شود. هیچ درخواستی، حتی با باگ در بک‌اند، نمی‌تواند داده‌ی سازمان دیگر را بخواند یا تغییر دهد.

الگو: **پایگاه داده و اسکیمای مشترک + ایزوله‌سازی در سطح ردیف (PostgreSQL Row-Level Security)**، با یک لایه‌ی دوم مستقل در ORM.

---

## ۱. نمای کلی

```
درخواست HTTP  ──►  TenantContextMiddleware  ──►  get_current_user  ──►  endpoint  ──►  SQLAlchemy Session
 Authorization:      JWT را رمزگشایی می‌کند:        tid توکن == سازمان     بدون هیچ شرط        │
 Bearer <JWT>        sub, tid → ContextVar           کاربر در دیتابیس؟      سازمانی در کد       │
                     (شناسه‌ی سازمان هرگز از                وگرنه 401                               ▼
                      پارامتر/بدنه خوانده نمی‌شود)                                   ┌── لایه‌ی ۱ (ORM) ────────────┐
                                                                                    │ do_orm_execute:              │
                                                                                    │  WHERE tenant_id = :tenant   │
                                                                                    │  روی SELECT/UPDATE/DELETE    │
                                                                                    │ before_flush: tenant_id خودکار│
                                                                                    └──────────────┬───────────────┘
                                                                                                   ▼
                                                                                    ┌── لایه‌ی ۲ (PostgreSQL RLS) ─┐
                                                                                    │ شروع هر تراکنش:              │
                                                                                    │  SET LOCAL ROLE ats_app      │
                                                                                    │  app.tenant_id / app.scope   │
                                                                                    │ پالیسی‌ها ردیف‌های بیگانه را  │
                                                                                    │ نامرئی می‌کنند (حتی SQL خام) │
                                                                                    └──────────────────────────────┘
```

| فایل | نقش |
|---|---|
| `app/core/tenancy.py` | Context درخواست (`ContextVar`)، Middleware، رویدادهای SQLAlchemy (نقش و متغیرهای RLS، فیلتر خودکار، پر کردن `tenant_id`) |
| `app/models/base.py` | `TenantMixin` (ستون اجباری) و `SharedTenantMixin` (اختیاری، برای مهارت‌ها) |
| `app/core/deps.py` | تطبیق `tid` توکن با سازمان واقعی کاربر |
| `app/core/tenant_provisioning.py` | ساخت سازمان (ثبت‌نام Admin و اسکریپت‌های داده‌ی آزمایشی) |
| `app/routers/tenants.py` | `GET /tenant` و مدیریت کارمندان سازمان |
| `alembic/versions/d2f6b8a41c37_…` | ستون‌ها، Backfill، قیدها، ایندکس‌ها، نقش `ats_app`، توابع و پالیسی‌های RLS |

## ۲. مدل داده

| جدول | `tenant_id` | توضیح |
|---|---|---|
| `jobs` · `applications` · `resumes` · `interviews` · `status_history` · `interview_question_sets` · `interview_questions` | اجباری (`NOT NULL`، FK ← `companies`، ایندکس) | داده‌ی عملیاتی سازمان |
| `skills` | اختیاری | خالی = مهارت استاندارد عمومی (همه می‌خوانند)؛ پر = مهارت سفارشی سازمان. نام در هر دامنه یکتاست (`uq_skills_tenant_name`) |
| `users` | اختیاری | کارمند (`Admin` / `HR_Manager` / `Interviewer`) عضو یک سازمان است؛ کارجو سازمان ندارد |
| `candidates` | ندارد | کارجو موجودیت سراسری است و می‌تواند به چند سازمان درخواست بدهد. هر سازمان فقط کارجویانی را می‌بیند که در خودش درخواست دارند |
| `companies` | خودِ Tenant | هر سازمان فقط ردیف خودش را می‌بیند |

**تعیین سازمان ردیف جدید:**
- **کارمند:** خودکار از Context (`before_flush`). اگر کد اشتباهی `tenant_id` سازمان دیگری بگذارد، `TenantAccessError` و پالیسی `WITH CHECK` جلویش را می‌گیرند.
- **کارجو (بدون سازمان):** رزومه و درخواست سازمانِ **صاحب آگهی** را می‌گیرند. پالیسی RLS هم بررسی می‌کند که `tenant_id` درخواست با `tenant_id` آگهی یکی باشد.
- **Worker ها (حالت system):** `tenant_id` را صریح از رکورد والد می‌خوانند. مثلاً سؤال‌های GenAI سازمانِ بانک سؤال را می‌گیرند، و رزومه‌ی ارسالی به سازمان دیگر هرگز وارد Prompt نمی‌شود.

## ۳. Context و توکن

| حالت | چه کسی | نقش دیتابیس | دسترسی |
|---|---|---|---|
| `tenant` | توکن دارای Claim `tid` (کارمند) | `ats_app` | فقط داده‌ی همان سازمان |
| `candidate` | توکن بدون `tid` | `ats_app` | پروفایل، درخواست‌ها و رزومه‌های خودش + آگهی‌های عمومی |
| `public` | بدون توکن معتبر | `ats_app` | فقط آگهی‌های عمومی (`GET /jobs/`) |
| `system` | Worker، زمان‌بند، مایگریشن، اسکریپت‌ها | نقش اصلی اتصال (مالک جدول‌ها، معاف از RLS) | همه‌چیز؛ کد خودش `tenant_id` را صریح فیلتر می‌کند |

- `tid` داخل JWT **امضاشده** است و کاربر نمی‌تواند عوضش کند. `get_current_user` در هر درخواست آن را با `users.tenant_id` تطبیق می‌دهد. توکن قدیمی بدون `tid`، توکن جعلی، یا کاربرِ منتقل‌شده به سازمان دیگر ← `401`.
- حالت پیش‌فرض بیرون از درخواست HTTP، `system` است. داخل درخواست فقط با `async with system_scope(db)` و فقط برای کار سطح پلتفرم استفاده می‌شود. تنها مورد فعلی، ساخت سازمان هنگام ثبت‌نام Admin است.

## ۴. پالیسی‌های RLS

نقش `ats_app` (`NOLOGIN`، `NOBYPASSRLS`) در شروع **هر تراکنش** درخواست API با `set_config('role', 'ats_app', true)` فعال می‌شود. همراهش متغیرهای `app.tenant_id`، `app.user_id` و `app.scope` تنظیم می‌شوند. همه با `SET LOCAL` هستند، پس با پایان تراکنش پاک می‌شوند و به اتصال بعدیِ Pool نشت نمی‌کنند.

| جدول | پالیسی‌ها (Permissive، با OR) |
|---|---|
| همه‌ی جدول‌های عملیاتی | `tenant_isolation`: `USING/WITH CHECK (tenant_id = app_current_tenant())` |
| `jobs` | `public_read`: خواندن برای `public` و `candidate` |
| `applications` | کارجو: خواندن، ثبت و پاسخ به پیشنهاد فقط برای خودش، و با `tenant_id` = سازمان آگهی |
| `resumes` | کارجو: خواندن و آپلود فقط برای خودش |
| `status_history` | کارجو: خواندن و ثبت فقط روی درخواست خودش |
| `candidates` | `candidate_self` + `tenant_applicants_read` (فقط متقاضیان همین سازمان) |
| `skills` | `shared_read` (استاندارد + سفارشی خود) + `tenant_custom` |
| `companies` | فقط ردیف خود سازمان |

- **Fail-Closed:** اگر Context تنظیم نشود (`app.tenant_id` خالی)، `app_current_tenant()` مقدار `NULL` برمی‌گرداند و هیچ ردیف عملیاتی دیده نمی‌شود.
- **بدون چرخه‌ی پالیسی:** `app_current_candidate_id()` تابع `SECURITY DEFINER` است (با `search_path` ثابت)، تا پالیسی `applications` برای پیدا کردن پروفایل کارجو از RLS جدول `candidates` عبور نکند.
- **پاسخ 404 به‌جای 403:** رکورد سازمان دیگر برای برنامه «وجود ندارد». پاسخ عیناً مثل شناسه‌ی ناموجود است و وجود رکورد افشا نمی‌شود.

## ۵. مایگریشن بدون قفل جدول (`d2f6b8a41c37`)

| گام | روش | قفل |
|---|---|---|
| افزودن ستون | `ADD COLUMN tenant_id uuid` بدون `DEFAULT` | لحظه‌ای (فقط متادیتا) |
| Backfill | دسته‌های ۵۰۰۰تایی، هر دسته یک تراکنش کوتاه | فقط قفل سطر |
| کلید خارجی | `NOT VALID` ← `VALIDATE CONSTRAINT` | `SHARE UPDATE EXCLUSIVE` (خواندن و نوشتن آزاد) |
| `NOT NULL` | `CHECK … NOT VALID` ← `VALIDATE` ← `SET NOT NULL` (بدون اسکن دوباره) ← حذف CHECK | لحظه‌ای |
| ایندکس | `CREATE INDEX CONCURRENTLY` (ایندکس نیمه‌کاره‌ی قبلی اول حذف می‌شود) | بدون قفل نوشتن |
| پالیسی‌ها / `ENABLE RLS` | پس از ساخت پالیسی‌ها | لحظه‌ای |

هر دستوری که قفل کوتاه `ACCESS EXCLUSIVE` لازم دارد، حداکثر **۳ ثانیه** (`lock_timeout`) منتظر می‌ماند. اگر تراکنش طولانی دیگری جلویش باشد، به‌جای صف‌کردن همه‌ی درخواست‌های بعدی پشت سر خودش کنار می‌کشد و تا ۲۰ بار با فاصله‌ی افزایشی دوباره تلاش می‌کند.

**داده‌های پیشین:** کارمندِ مالک یک شرکت ← همان شرکت. بقیه‌ی کارمندان و رکوردهای بی‌مالک ← «سازمان پیش‌فرض (داده‌های پیشین)»، با مالکیت قدیمی‌ترین Admin. رکوردهای فرزند (درخواست، مصاحبه، تاریخچه، بانک سؤال) سازمان والدشان را می‌گیرند. رزومه سازمان قدیمی‌ترین درخواست کارجو را می‌گیرد. هیچ ردیفی حذف یا بی‌سازمان نمی‌ماند.

**آزمون خودکار** (`tests/integration/test_tenancy_migration.py`):
- دیتابیس با داده‌ی قدیمی روی نسخه‌ی قبلی ساخته می‌شود و یک تراکنش طولانی قفل `jobs` را نگه می‌دارد.
- مایگریشن هم‌زمان اجرا می‌شود، مسیر `lock_timeout` و تلاش دوباره را طی می‌کند و موفق تمام می‌شود.
- خواندن‌های هم‌زمان کمتر از ۴٫۵ ثانیه منتظر می‌مانند.
- تعداد ردیف‌ها قبل و بعد یکی است.

نقش `ats_app` در `downgrade` حذف نمی‌شود: نقش‌ها در سطح کل سرور PostgreSQL هستند و دیتابیس‌های دیگر ممکن است از آن استفاده کنند.

## ۶. ورود سازمان جدید (Onboarding)

| مسیر | دسترسی | توضیح |
|---|---|---|
| `POST /auth/register` با `role=Admin` | عمومی | `company_name` الزامی است. سازمان تازه ساخته می‌شود و Admin مالکش می‌شود |
| `POST /auth/register` با `role=HR_Manager / Interviewer` | — | `422`: کارمند ثبت‌نام عمومی ندارد |
| `POST /tenant/users` | `Admin` | ساخت حساب HR یا Interviewer در همان سازمان |
| `GET /tenant/users` | `Admin` | فهرست کارمندان سازمان |
| `GET /tenant` | کارمندان | مشخصات سازمان |

هشدارهای زیرساخت (`/ops/*`) فقط به Admin های **سازمان گرداننده‌ی پلتفرم** (`OPS_ALERT_TENANT_ID`، پیش‌فرض سازمانِ قدیمی‌ترین Admin) می‌رسند، نه به Admin سازمان‌های مشتری.

| توکن بدون `tid` یا با `tid` جعلی | `401` |

## ۸. محدودیت‌ها و قدم‌های بعدی

- **نقش اتصال:** اپلیکیشن هنوز با نقش مالک جدول‌ها وصل می‌شود و در هر تراکنش به `ats_app` سوئیچ می‌کند. این مدل در برابر باگِ فراموش کردن فیلتر محافظت می‌کند، ولی SQL Injection می‌تواند `RESET ROLE` بزند. قدم بعدی برای Production: اتصال API با یک نقش LOGIN مستقل و بدون `BYPASSRLS`، و نگه‌داشتن نقش مالک فقط برای مایگریشن و Worker ها.
- **پنجره‌ی استقرار:** بین اجرای مایگریشن و بالا آمدن نسخه‌ی جدید، نسخه‌ی قدیمی (بدون `tenant_id`) نمی‌تواند ردیف عملیاتی جدید بنویسد (`NOT NULL`). خواندن‌ها بدون مشکل ادامه دارند.
- **دسترسی چندسازمانی کارمند:** هر کارمند فقط عضو یک سازمان است (`users.tenant_id`). عضویت چندگانه جدول واسط و انتخاب سازمان فعال هنگام ورود را لازم دارد.
- `jobs.company_id` قدیمی حفظ شده است. مرجع مالکیت `tenant_id` است.
