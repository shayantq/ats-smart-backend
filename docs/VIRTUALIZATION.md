# مجازی‌سازی و دریافت مرحله‌ای کانبان

## پیاده‌سازی

`@tanstack/react-virtual` در فرانت‌اند نصب شد. هر ستون viewport عمودی محدود و اندازه‌گیری ارتفاع واقعی دارد؛ overscan برابر ۲ ردیف است. ستون‌های افقی خارج از دید، کارت عادی نصب نمی‌کنند. کارت دارای فوکوس، انتخاب مقصد، drag یا پروندهٔ باز می‌تواند جداگانه نگه داشته شود. کلید ردیف شناسهٔ درخواست است و جایگاه بازیافتی هویت کارجو نیست.

`useKanbanPages.ts` برای هر وضعیت یک infinite query مستقل با کلید آگهی/وضعیت و صفحهٔ ۵۰تایی دارد. هر وضعیت فقط صفحهٔ اول را ابتدا می‌گیرد و صفحهٔ بعد در نزدیکی انتها یا با دکمهٔ «بارگذاری بیشتر» دریافت می‌شود. cursor به‌صورت opaque استفاده می‌شود؛ دریافت تکراری هم‌زمان قفل می‌شود، cursor تکراری پایان دریافت است و شناسه‌های تکراری هنگام تجمیع حذف می‌شوند. خطای صفحهٔ بعد، دادهٔ موجود را نگه می‌دارد و دکمهٔ تلاش مجدد دارد. تغییر آگهی cache مستقل و نمونهٔ تازهٔ بورد می‌سازد.

با تأیید کاربر، API قبلی به شکل افزایشی توسعه یافت:

- `GET /api/v1/applications/?job_id=...&current_status=...`: فیلتر اختیاری وضعیت، با همان cursor و ترتیب قبلی؛ درخواست‌های بدون این پارامتر تغییری ندارند.
- `GET /api/v1/applications/counts?job_id=...`: شمارش گروهی واقعی وضعیت‌ها؛ همان نقش‌های Admin/HR و محدودیت tenant دیتابیس. شمارش ناموجود در رابط با تعداد «بارگذاری‌شده» معرفی می‌شود و total ساختگی ندارد.

تغییر دیتابیس، migration یا ایندکس انجام نشد. تعداد درخواست‌های آغازین حداکثر ۹ صفحهٔ مستقل به‌علاوهٔ counts است؛ دانلود تمام صفحات برای پیدا کردن ستون انتهایی انجام نمی‌شود.

## تعامل و کش

Arrowها روی فهرست منطقی کار می‌کنند: مقصد خارج از DOM ابتدا scroll/mount و سپس focus می‌شود. عبور از مرز صفحهٔ بارگذاری‌شده، دادهٔ بعد را می‌گیرد و پس از رسیدن، فوکوس را جلو می‌برد؛ اگر کاربر جای دیگری رفته باشد فوکوس دزدیده نمی‌شود. پرونده به سطح بورد منتقل شده تا با بازیافت کارت بسته نشود.

انتقال با همان قوانین و mutation انجام می‌شود. تغییر خوش‌بینانه در overlay فقط همان شناسه است؛ rollback کل صفحات کش‌شده را بازنویسی نمی‌کند. بعد از پاسخ، صفحات دو ستون درگیر از ابتدا با سرور تطبیق و شمارش‌ها تازه می‌شوند. این کار مرز cursor متکی به updated_at را پس از جابه‌جایی معتبر نگه می‌دارد. کارت جابه‌جاشده به کمک شناسه دوباره فوکوس می‌گیرد. سایر ستون‌ها و صفحاتشان حفظ می‌شوند.

`React.memo` کارت و memo شدن کنترل‌های کارت در ستون، بازسازی فرزندان ثابت در هر فریم اسکرول را کاهش می‌دهد. آرایهٔ تجمیع و گروه‌بندی نیز فقط هنگام تغییر داده یا overlay محاسبه می‌شوند. پنل مستقل جست‌وجوی کارجو یا جدول آماری رکوردی در کد فعلی یافت نشد؛ صفحهٔ جدیدی ساخته نشده است.

## نتایج اندازه‌گیری

سنجش با `frontend/virtual-check.cjs` روی build واقعی و API مصنوعی loopback، مجموعهٔ ۱۰هزارنفری، viewport برابر ۱۴۴۰×۱۰۰۰ و بدون throttle شبکه/CPU اجرا شد. هر دور context تازه داشت و پاسخ HTTP بدون cache بود؛ مرورگر مشترک است. پنج اجرای سرد برای هر حالت ثبت شد. مشخصات CPU، RAM و نسخهٔ مرورگر در `performance.json` است.

| حالت | بازهٔ آماده‌شدن اولین بورد قابل تعامل | p95 پنج اجرا | کارت نصب‌شده |
|---|---|---|---|
| دریافت صفحه‌ای | ۲۱۹ تا ۲۶۳ میلی‌ثانیه | ۲۶۳ میلی‌ثانیه | ۲۵ تا ۲۹ |
| stress با تمام ۱۰هزار رکورد در حافظه | ۲۵۷ تا ۳۴۱ میلی‌ثانیه | ۳۴۱ میلی‌ثانیه | ۲۵ تا ۲۶ |

این عدد عملیاتی از آغاز navigation تا آماده‌بودن بورد و کارکرد Enter برای انتخاب مقصد است؛ نام آن metric رسمی Lighthouse TTI نیست و به معنی دانلود تمام ۱۰هزار رکورد در حالت صفحه‌ای نیست. تعداد کل elementهای اولیه ۳۳۳ بود؛ تعداد کارت و تعداد تمام تگ‌ها عمداً جدا شمرده شده‌اند.

در نمونهٔ trace اسکرول، p95 فاصلهٔ `AnimationFrame::Presentation` حدود ۷ تا ۸ میلی‌ثانیه، فاصلهٔ بیش از ۱۶٫۷ میلی‌ثانیه صفر و long task بیش از ۵۰ میلی‌ثانیه صفر بود. traceهای CDP ذخیره شده‌اند. این شاهد عملکرد مرورگر headless روی همین سخت‌افزار است؛ تضمین نمایشگر فیزیکی یا شبکهٔ تولید نیست. انتهای فهرست کامل با کارت ۹۸۹۹ نیز باز شد. heap در سناریوی stress حدود ۲۳ تا ۳۱ مگابایت بود؛ این نمونهٔ کوتاه ادعای نبود نشت در اجرای بلندمدت نیست و حافظهٔ داده‌های cache همچنان با تعداد رکوردهای دریافت‌شده رشد می‌کند.

## راستی‌آزمایی

- `npm run build`: موفق.
- `npm test -- --runInBand`: ۴۹ تست در ۱۲ مجموعه موفق.
- `pytest tests/integration/test_applications_api.py -q`: هشت تست روی دیتابیس موقت PostgreSQL محلی موفق؛ شامل cursor فیلترشده، counts، جداسازی tenant و منع نقش Candidate.
- `virtual-check.cjs`: دو تم × سه عرض ۳۷۵، ۷۶۸، ۱۴۴۰؛ حرکت کیبورد از مرز صفحه و بازماندن پرونده هنگام scroll موفق، بدون سرریز صفحه.
- `a11y-check.cjs` با خروجی جداگانه: جریان کیبورد، انتقال موفق/ناموفق و rollback و dialog موفق؛ Lighthouse Accessibility در دو تم ۱۰۰.
- روی API واقعی localhost، آگهی مجزای ۱۰هزارنفری با دادهٔ ساختگی ساخته شد و ۱۶ کارت نصب‌شده مشاهده شد. عبور کیبورد از ۵۵ کارت، انتقال واقعی یک رکورد مصنوعی و rollback انتقال بعدی با پاسخ خطای ساختگی موفق بودند.
- شمارش DOM و trace جای تست شنیداری صفحه‌خوان را نمی‌گیرد؛ معیار صوتی قبلی همچنان تأیید نشده است.

تست E2E کانبان برای دیدن کارت ستون افقی خارج از دید، ابتدا همان ستون را به viewport می‌آورد. اجرای کامل Docker E2E این دور انجام نشده است؛ تست مرورگرِ build با fixture و تست API واقعی محلی جداگانه اجرا شده‌اند.

## شواهد

پوشهٔ `training/reports/virtual/`: `performance.json`، `interaction.json`، `trace-paged.json`، `trace-stress.json`، `scroll-paged.json`، `scroll-stress.json`، `backend-tests.txt`، `unit-final.txt`، `local-interaction.json` و `localhost-10000.png`. تصاویر `keyboard-{light,dark}-{375,768,1440}.png` و `stress-last-record.png` ساختگی‌اند. گزارش Lighthouse جدید در زیرپوشهٔ `a11y/` است.

ابزار بازتولید به build هم‌مبدأ نیاز دارد: در PowerShell از `frontend/`، `$env:VITE_API_BASE_URL='/api/v1'; npm run build` و سپس از ریشه `node frontend/virtual-check.cjs`. این متغیر تنظیمات تولید را تغییر نمی‌دهد. برای دور a11y خروجی را با `ATS_A11Y_OUTPUT='../training/reports/virtual/a11y'` جدا کنید.

## تست دستی لوکال

۱. `http://localhost:5173` را باز و Ctrl+Shift+R بزنید؛ با حساب HR آزمایشی قبلی وارد شوید. از فهرست آگهی، «آزمون مجازی‌سازی — ۱۰٬۰۰۰ کارجوی ساختگی» را انتخاب کنید.

۲. داخل خود ستون پیش‌نویس اسکرول کنید؛ صفحهٔ بعد باید نزدیک انتها دریافت شود. «بارگذاری بیشتر» نیز با Tab و Enter قابل استفاده است. شمارندهٔ بالای ستون total سرور است، نه تعداد کارت‌های DOM.

۳. با Tab به کنترل «تغییر وضعیت» برسید و ArrowDown را بیش از ۵۰ بار بزنید؛ فهرست باید همراه فوکوس جلو برود و صفحهٔ بعد خودکار برسد. Enter مقصد را انتخاب، جهت‌ها آن را عوض و Escape لغو می‌کند. تأیید نهایی با Enter/Space واقعاً دادهٔ آزمایشی را تغییر می‌دهد.

۴. پروندهٔ یک کارت را باز و Escape را امتحان کنید؛ نبود رزومهٔ مرتبط برای رکوردهای مصنوعی جدید حالت خالی واقعی است. آگهی قبلی شش پروندهٔ پرشده را همچنان دارد.

۵. در Console مرورگر `document.querySelectorAll('[data-testid="application-card"]').length` را قبل و بعد از اسکرول ببینید؛ عدد باید کوچک بماند. در Network درخواست‌های `current_status` و `cursor` را ببینید؛ fetch همهٔ صفحات در شروع نباید وجود داشته باشد.

۶. تم روشن/تاریک و عرض موبایل را عوض و بین آگهی قدیمی و آگهی بزرگ جابه‌جا شوید؛ کارت آگهی قبلی نباید با دیگری مخلوط شود.

تغییرات فقط محلی‌اند؛ commit، push و deploy انجام نشده است. API و دادهٔ مصنوعی فقط در محیط اختصاصی پیش‌نمایش محلی تغییر کرده‌اند.
