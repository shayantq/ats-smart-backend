# آموزش تکمیلی LoRA روی دیتاست ATS

آموزش کامل یک مدل زبانی چند میلیارد پارامتری به چند GPU پرحافظه نیاز دارد. با **QLoRA** وزن‌های مدل پایه
۴ بیتی و منجمد می‌مانند و فقط دو ماتریس کم‌رتبه‌ی کوچک (A و B) کنار لایه‌های هدف آموزش می‌بینند؛ خروجی یک
«آداپتر» چند ده مگابایتی است که روی همان مدل پایه سوار می‌شود. کد: `training/lora/`.

> **داده‌ی این اجرا ساختگی است.** ورودی لوکال از seeder قبلی ساخته شده و شامل ۸٬۲۵۳ رکورد آموزش، ۱٬۰۳۳
> اعتبارسنجی و ۱٬۰۳۲ تست است. اجرای ۹۰۰گامی و ارزیابی نهایی با شواهد زیر تأیید شدند. نتیجه‌ی چنین
> اجرایی فقط شاهدی برای روش و زیرساخت است، نه کیفیت روی بازار کار واقعی. وضعیت فعلی دیتابیس Production
> در این کار بررسی یا تغییر داده نشده است.

**نتیجهٔ نهایی در ۲۰۲۶-۱۱-۰۹، ساعت ۱۸:۳۱ تهران: معیارهای پذیرش اجرای ۹۰۰گامی پاس شدند؛ وضعیت completed است.**
برنامهٔ اولیهٔ ۱٬۰۳۲ گام و دو epoch کامل نشد؛ این تصمیم کاربر است، نه فعال‌شدن early stopping.
بهترین checkpoint گام ۹۰۰ با loss اعتبارسنجی 0.0396325886 است. validation کامل ۱٬۰۳۳ نمونه با loss
برابر 0.0395322368 تمام شد؛ خروجی آداپتر، بررسی همگرایی، بارگذاری مجدد و تست نهایی انجام شدند.
تعداد تست نهایی با درخواست صریح کاربر از ۲۰۰ به **۱۰۰ نمونهٔ ثابت و لایه‌بندی‌شده** تغییر کرد؛ معیارهای همگرایی
تغییر نکرده‌اند. وضعیت زنده و نتیجهٔ نهایی در `training/reports/ats-20261108-fast-01-workflow/status.json` است.

## محیط

| مورد | مقدار |
|------|-------|
| سخت‌افزار | GPU لپ‌تاپ انویدیا با ۶ گیگابایت VRAM (پشتیبانی bf16) |
| وابستگی‌ها | `requirements-train.txt` (torch با CUDA 13.0، transformers، peft، bitsandbytes، accelerate، tensorboard، matplotlib) — جدا از `requirements.txt`؛ وارد ایمیج Production و CI نمی‌شود |
| بررسی محیط | `python -m training.lora.gpu_check` (CUDA، bf16 و یک ضرب ماتریسی واقعی ۴ بیتی) |
| مدل پایه | یک مدل Instruct حدود ۳ میلیارد پارامتری از **همان خانواده‌ی توکنایزر** دیتاست (`data/tokenizer`)، تا شمارش توکن اعتبارسنجی‌شده‌ی دیتاست درست بماند. شناسه‌اش فقط در `training/lora/model.env` (در .gitignore؛ نمونه: `model.env.example`) |

```powershell
pip install --resume-retries 20 --retries 10 --timeout 120 -r requirements-train.txt
copy training\lora\model.env.example training\lora\model.env   # و پر کردن LORA_BASE_MODEL_REPO
python -m training.lora.gpu_check
python -m training.lora.download --out models/base-model --workers 8 --attempts 3
```

`transformers` روی 5.15.1 ثابت شده: نسخه‌های 5.16 به بعد `tokenizers>=0.23` می‌خواهند و با نسخه‌ی ثابت برنامه
(`tokenizers==0.22.1`) در یک venv ناسازگارند. کتابخانه‌ی `datasets` لازم نشد (JSONL مستقیم خوانده می‌شود).

دانلود از commit ثابت مخزن، به بخش‌های ۴ مگابایتی و با ۸ اتصال انجام می‌شود. بخش‌های ناقص در
`models/base-model/.parts` باقی می‌مانند؛ اجرای دوباره از همان نقطه ادامه می‌دهد. هر بخش حداکثر سه تلاش دارد.
فایل نهایی فقط پس از تأیید اندازه و SHA-256 (برای LFS) یا Git Blob SHA-1 جایگزین می‌شود. فایل
`download_manifest.json` فقط پس از تأیید همه‌ی فایل‌ها ساخته می‌شود؛ نبود وزن یا عدم تطابق tokenizer کد خروج
غیرصفر دارد. فضای لازم برای بخش‌ها و مونتاژ موقت هر shard پیش از دریافت بررسی می‌شود.

## پیکربندی و دلیل هر مقدار (`training/lora/config.py`)

| پارامتر | مقدار | چرا |
|---------|-------|-----|
| کوانتیزاسیون | NF4، double quant، محاسبه bf16 | NF4 برای توزیع نرمال وزن‌ها بهینه است؛ double quant حدود ۰٫۴ بیت بر پارامتر دیگر صرفه‌جویی می‌کند؛ bf16 روی این GPU بومی و پایدارتر از fp16 است |
| `r` (رتبه) | 16 | برای تطبیق دامنه (قالب خروجی + اصطلاحات HR) کافی است؛ ۸ ظرفیت کمی برای خروجی ساختاریافته‌ی طولانی دارد و ۳۲/۶۴ حافظه و خطر حفظ‌کردن داده را بالا می‌برد |
| `lora_alpha` | 32 | ضریب مقیاس `alpha/r = 2` — مقدار رایج و پایدار؛ با lr = 2e-4 به‌روزرسانی‌ها نه کند و نه ناپایدارند |
| `lora_dropout` | 0.05 | منظم‌سازی سبک در برابر بیش‌برازش روی دیتاستی با الگوی تکراری؛ مقدار بیشتر همگرایی را کند می‌کند |
| `bias` | none | بایاس‌ها منجمد؛ آداپتر کوچک و قابل سوار شدن روی همان مدل پایه می‌ماند |
| `target_modules` | q/k/v/o_proj + gate/up/down_proj | همه‌ی لایه‌های خطی توجه و MLP؛ تطبیق فقط روی توجه برای یادگیری قالب خروجی جدید کافی نیست. وجود هر نام پیش از آموزش در معماری مدل بررسی می‌شود (تعداد هر ماژول در لاگ) |
| `max_seq_len` | 2048 | بلندترین رکورد دیتاست ۱٬۶۰۹ توکن است؛ رکورد بلندتر **حذف و شمرده** می‌شود، هرگز بی‌صدا بریده نمی‌شود |
| batch × accumulation | 1 × 16 | batch مؤثر ۱۶ با ۶ گیگابایت VRAM |
| learning rate | 2e-4، cosine، warmup ۳٪ | مقدار استاندارد QLoRA؛ warmup جهش‌های اولیه‌ی گرادیان را مهار می‌کند |
| epochs | 2 | با توقف زودهنگام؛ داده‌ی ساختگی الگوی تکراری دارد و epoch بیشتر بیش‌برازش می‌آورد |
| بهینه‌ساز | paged_adamw_8bit | حالت بهینه‌ساز ۸ بیتی و صفحه‌بندی‌شده — جلوی OOM لحظه‌ای را می‌گیرد |
| gradient checkpointing | روشن | ذخیره نکردن activation ها؛ تنها راه جا شدن توالی ۲۰۴۸ در ۶ گیگابایت |
| eval | هر ۵۰ گام روی ۳۰۰ رکورد ثابت validation | زیرمجموعه‌ی لایه‌بندی‌شده بر اساس سطل نمره با seed ثابت (eval کامل هر بار حدود ۲ ساعت به اجرا اضافه می‌کرد)؛ در پایان یک eval کامل روی همه‌ی validation |
| توقف زودهنگام | patience = 3 روی eval_loss، بارگذاری بهترین checkpoint | جلوی ادامه‌ی آموزش پس از شروع بیش‌برازش |

## داده و ماسک loss (`training/lora/data.py`)

هر رکورد با قالب چت خود توکنایزر رندر می‌شود (`system`=instruction، `user`=input، `assistant`=output). برچسب همه‌ی
توکن‌های system/user و padding برابر `-100` است، پس **loss فقط روی پاسخ** حساب می‌شود: مدل یاد می‌گیرد ارزیابی
JSON تولید کند، نه متن رزومه و آگهی را حفظ کند. اگر قالب چت پیشوند ثابتی برای پاسخ نسازد، آموزش با خطا متوقف می‌شود.

قبل از آموزش، تعداد رکوردها با `stats.json` و `manifest.json` تطبیق داده می‌شود. گروه کارجو و ورودی یکسان
نباید میان train، validation و test مشترک باشد. اثر انگشت توکنایزر مرجع و واژگان مدل هم کنترل می‌شوند.
توکنایزر مرجع باید در `data/tokenizer/tokenizer.json` کنار پوشه‌ی دیتاست باقی بماند.

## اجرا و پایش

```powershell
python -m training.lora.train --run-id smoke-01 --smoke             # ۳۰ گام، eval روی ۳۰ رکورد؛ فقط تشخیصی
python -m training.lora.train --run-id main-01                       # اجرای کامل، پس از بررسی زمان تخمینی
python -m training.lora.train --run-id main-01 --resume              # ادامه از آخرین checkpoint پس از قطعی
tensorboard --logdir training/runs                                             # پایش زنده: http://localhost:6006
```

هر خط لاگ پیشرفت (JSON) گام، loss، eval_loss، زمان هر گام، پیک VRAM و زمان باقی‌مانده را از مقادیر واقعی نشان می‌دهد.

`--smoke` فقط مسیر آموزش را آزمایش می‌کند و جای اجرای کامل یا معیار همگرایی نیست. این حالت اعتبارسنجی کامل
۱٬۰۳۳ رکوردی را اجرا نمی‌کند. `run_summary.json` نوع اجرا، انجام‌شدن اعتبارسنجی کامل و برآورد زمان اجرای کامل
از زمان واقعی گام‌ها و eval را ثبت می‌کند. برآورد شامل دانلود نیست و هزینه‌ی ذخیره‌ی checkpoint و نوسان دما/بار
GPU می‌تواند آن را افزایش دهد. اگر برآورد بیشتر از ۱۲ ساعت شد، اجرای کامل منتظر تصمیم کاربر می‌ماند.

نام اجرای استفاده‌شده بدون `--resume` بازنویسی نمی‌شود. ادامه به checkpoint و همان پیکربندی و اثر انگشت
دیتاست نیاز دارد. مسیر TensorBoard هر اجرا جداست. فقط ماتریس‌های LoRA مجاز به دریافت گرادیان‌اند؛ وجود
پارامتر قابل آموزش در وزن‌های پایه خطاست. برای کاهش حافظه‌ی اعتبارسنجی فقط loss ذخیره می‌شود، نه logits.

## خروجی و ارزیابی

- `training/outputs/<run>/adapter/`: `adapter_config.json` + `adapter_model.bin` (با `safe_serialization=False`) و
  توکنایزر؛ `trainer_state.json`. وزن آداپتر و مدل پایه هرگز وارد ریپو نمی‌شوند.
- `python -m training.lora.evaluate --adapter training/outputs/<run>/adapter --report training/reports/<run>/evaluation.json`
  در یک پردازه‌ی تازه مدل پایه + آداپتر را بارگذاری و برای ۲۰۰ رکورد ثابت test پاسخ تولید می‌کند: نرخ JSON معتبر،
  نرخ نمره‌ی معتبر و MAE نمره، در کنار MAE یک پیش‌بینی ثابت (میانگین نمره‌ی train) برای مقایسه.

پیش از اجرای واقعی بررسی شده‌اند؛ مقدار آستانه‌های ۴۰٪، ۰٫۳۵ و سه افزایش پیاپی تغییر نکرده است.

مبنای کتابخانه‌ها: [آموزش روی وزن کوانتیزه](https://huggingface.co/docs/peft/developer_guides/quantization)،

## نتایج اجرا

بررسی محلی ۲۰۲۶-۱۱-۰۷:

- GPU: RTX 4050 Laptop، VRAM شش گیگابایت، درایور 621.01، CUDA runtime 13.0، پشتیبانی bf16.
- `gpu_check`: موفق؛ خطای نسبی ضرب ماتریسی NF4 برابر 0.00376.
- نسخه‌ها با `requirements-train.txt` تطبیق دارند؛ `TrainingArguments` با کتابخانه‌ی نصب‌شده ساخته شد.
- توکن‌سازی قبل از اصلاحات: ۸٬۲۵۳ آموزش، ۳۰۰ eval میانی و ۱٬۰۳۳ validation کامل، بدون حذف رکورد بلند.
- ۳۹ تست قبلی پاس شدند. پس از افزودن بررسی‌ها، ۵۴ تست LoRA پاس شدند؛ آزمون مدل کوچک CPU نشان داد
  فقط آداپتر تغییر می‌کند، هر دو فایل صادر می‌شوند و logits پس از بارگذاری دوباره یکسان‌اند. این آزمون
  جای آموزش مدل اصلی روی GPU را نمی‌گیرد.
- دانلود مدل اصلی به درخواست کاربر متوقف شده؛ اندازه‌ی داده‌ی وزن‌ها حدود ۶٬۱۷۲ مگابایت ده‌دهی است. این عدد اندازه‌ی
  مدل پایه است، نه اندازه‌ی آداپتر. هنوز هیچ اندازه یا کیفیتی برای آداپتر اجرای اصلی اندازه‌گیری نشده است.
- آموزش GPU، نمودار واقعی loss، نتیجه‌ی همگرایی و ارزیابی ۲۰۰ رکورد تست: **هنوز انجام نشده**.

## نقطه‌ی توقف و ادامه‌ی کار

تسک به درخواست کاربر در ۲۰۲۶-۱۱-۰۷ موقتاً کنار گذاشته شد تا تسک بعدی انجام شود. هیچ پردازه‌ی دانلودی فعال
نمانده و workflow آموزش و TensorBoard راه‌اندازی نشده‌اند. کاربر دو shard وزن را دستی دانلود می‌کند و بعد
مسیرشان را اعلام می‌کند. فایل‌های کوچک مدل و tokenizer در `models/base-model/` موجودند؛ بخش‌های ناقص
دانلود قبلی (حدود ۱٫۱۲ گیگابایت ده‌دهی) در `.parts/` حفظ شده‌اند.

عوض‌شده و آموزش وزن پایه جلوگیری می‌کند؛ `--smoke` از آموزش کامل جداست. `download.py` دریافت محدوده‌ای و

دروازه‌ی همگرایی تاریخچه‌ی ناکافی، loss نامعتبر و اعتبارسنجی بدون بهبود را رد می‌کند؛ آستانه‌ها کم نشده‌اند.

شواهد فعلی: ۱۷۶ تست LoRA و دیتاست قبلی پاس شدند؛ پس از افزودن workflow، هر ۱۰ تست فایل
`test_lora_training.py` (شامل چهار سناریوی مرز زمان) هم پاس شدند. `pip check` سالم است. Black اجرا شد؛
Flake8 پیش از اضافه‌شدن workflow سالم بود و باید در ادامه روی وضعیت نهایی دوباره اجرا شود.
بررسی واقعی دیتاست، نبود هم‌پوشانی سه بخش و تطابق واژگان tokenizer را تأیید کرد.

### بهینه‌سازی حافظه‌ی loss پیش از اجرای کامل

اجرای اولیه‌ی `smoke-20261108-01` پس از سه گام برای مقایسه متوقف شد؛ زمان گام‌ها حدود ۷۷ تا ۸۱ ثانیه و
اوج حافظه‌ی ثبت‌شده در سه گام تا ۶٫۲۷ گیگابایت رسید. این اجرای کوتاه، اجرای سی‌گامی کامل یا شاهد همگرایی نیست.
لاگ‌های آن برای مقایسه حفظ شده‌اند.

متن کامل ورودی همچنان وارد Transformer می‌شود. برای کاهش حافظه، فقط logits موقعیت‌هایی که هدف بعدی‌شان
پاسخِ بدون ماسک است ساخته می‌شوند؛ `logits_to_keep` و `shift_labels` کتابخانه همان هم‌ترازی علّی و مخرج
نرمال‌سازی loss را حفظ می‌کنند. هیچ رکورد یا توکن پاسخ حذف یا بریده نمی‌شود. این رفتار با
`TrainSettings.answer_logits_only` در مشخصات اجرا ثبت می‌شود و مدل، داده، تعداد epoch و تنظیمات LoRA عوض نشده‌اند.

آزمون روی مدل کوچک هم‌معماری، مقدار loss و گرادیان تک‌تک ماتریس‌های LoRA را برای هر دو حالت نرمال‌سازی
مقایسه و برابری با تلورانس 1e-6 را تأیید کرد. ۱۸۳ تست مرتبط و Flake8 پاس شدند. اجرای GPU تازه با نام
`smoke-20261108-02` شروع شد؛ اولین گام ۴۰٫۳۸ ثانیه، اوج حافظه‌ی تخصیص‌یافته ۴٫۵۱ گیگابایت و همان loss
۱٫۲۰۳۶ داشت. نتیجه‌ی نهایی سی گام، اعتبارسنجی و برآورد اجرای کامل هنوز باید ثبت شوند.

### بازیابی پس از کرش ویندوز

اجرای `smoke-20261108-02` تا گام ۱۱ پیش رفت، ولی در backward بعدی خطای CUDA out of memory رخ داد.
checkpoint گام ۱۰ با وزن آداپتر ۱۱۹٬۸۰۱٬۵۲۸ بایت، وضعیت optimizer و RNG حفظ شد. در گام ۱۰، loss اعتبارسنجی
۳۰ رکورد ثابت برابر 0.1218404 و زمان همان eval برابر ۲۵٫۸۶ ثانیه بود؛ این شواهد محدود، پذیرش آموزش کامل نیستند.
زمان گام‌های این بخش حدود ۴۰ تا ۴۵ ثانیه و اوج حافظهٔ تخصیص‌یافته تا ۴٫۵۸ GiB بود.

تلاش اول ادامه هنگام بارگذاری مدل با خطای Windows 1455 (کمبود pagefile) متوقف شد. در بررسی پیش از کرش،
فضای آزاد C حدود ۰٫۲۵ GiB بود. پس از راه‌اندازی مجدد ویندوز، فضای آزاد حدود ۶۹ GiB اندازه‌گیری شد؛ علت قطعی
بلک‌اسکرین تعیین نشده است و رویداد Kernel-Power 41 فقط خاموشی غیرمنتظره را تأیید می‌کند. فایل‌های اصلی
Downloads و نسخه‌های مدل داخل پروژه باقی‌اند؛ تبدیل به hard link در وضعیت فعلی تأیید نشده است.

به درخواست کاربر، فقط تنظیمات **محلی** WSL بهینه شد: سقف RAM از ۶ به ۴ GB، پردازنده‌ها ۴، swap همان ۲ GB
و `autoMemoryReclaim=dropCache` حفظ شد. پشتیبان تنظیمات قبلی در
`C:\Users\shaya\.wslconfig.before-lora-20261108-140925.bak` است. Docker Desktop محلی به‌شکل عادی متوقف و
دوباره راه‌اندازی شد؛ سقف واقعی Linux و سلامت کانتینرهای محلی تأیید شدند. سرور و تنظیمات استقرار تغییر نکردند.

`resources.py` قبل از واردکردن torch و بارگذاری مدل، حداقل احتیاطی ۸ GiB commit آزاد ویندوز را بررسی می‌کند؛
پس از بارگذاری و بین ریزگام‌های gradient accumulation، حد ۲ GiB commit و ۲ GiB فضای آزاد دیسک کنترل می‌شود.
کمبود منابع اجرای جاری را با خطا متوقف می‌کند و checkpoint قبلی دست‌نخورده می‌ماند؛ این محافظ تضمین جلوگیری
از کرش سیستم نیست. اندازه‌گیری بر پایهٔ API رسمی
[GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex)
است؛ تنظیمات pagefile ویندوز تغییر داده نشد. `torch_empty_cache_steps=1` برای آزادکردن کش بلااستفادهٔ CUDA
فعال است؛ مدل، داده و هایپرپارامترهای پایه عوض نشده‌اند.

عادی logits حفظ می‌شود. آزمون مدل کوچک برای هر دو روش نرمال‌سازی، برابری دقیق loss و تمام گرادیان‌های LoRA
را تأیید کرد. پس از این اصلاح، ۲۶ تست `test_lora_training.py` و `test_lora_data.py` و Flake8 پاس شدند.
