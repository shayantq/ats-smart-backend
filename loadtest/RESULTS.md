# نتایج تست بار — ۵۰۰۰ کارجوی هم‌زمان

تاریخ اجرا: ۲۰ و ۲۱ مهر ۱۴۰۵ · ابزار: Locust 2.31.8 (۱ Master + ۴ Worker) · داده‌ی خام: `loadtest/reports/*.csv`

## محیط تست

| | |
|---|---|
| سخت‌افزار | یک لپ‌تاپ: Intel Core i5-13420H (۱۲ رشته)، ۲۴ گیگ رم — Docker با ۱۲ هسته و ۶ گیگ رم |
| سیستم | کل استک واقعی Docker: Nginx → ۶ نسخه‌ی بک‌اند FastAPI → PostgreSQL 16 + Redis + Worker |
| نکته | تولیدکننده‌ی بار (Locust)، سرور و دیتابیس همه روی **همین یک دستگاه** اجرا شدند و برای CPU رقابت می‌کردند؛ روی سرور جدا نتایج بهتر خواهد بود |

## سناریو

هر کاربر مجازی = یک کارجوی واقعی با حساب یکتای خودش (۵۰۰۰ حساب):
1. **ورود** (`POST /auth/login`، با Bcrypt واقعی) — یک بار
2. **آپلود رزومه** (`POST /resumes/upload`، فایل PDF واقعی) — یک بار
3. **مرور مداوم**: لیست آگهی‌ها، رهگیر وضعیت درخواست، پروفایل

افزایش تدریجی: ۲۵ کاربر جدید در ثانیه تا ۵۰۰۰ کاربر. Rate Limit ورود روشن ماند (هر کاربر مجازی IP جدا).

## نتایج

### دور ۲ — رفتار واقعی کاربر (۵ تا ۱۵ ثانیه بین کلیک‌ها) ✅

| مرحله | درخواست‌ها | خطا / 502 / 504 | میانه | صدک ۹۵ | صدک ۹۹ | بیشینه |
|---|---|---|---|---|---|---|
| **اوج: ۵۰۰۰ کاربر فعال** (~۶ دقیقه، ~۵۰۰ درخواست/ثانیه) | ۱۸۱,۰۶۴ | **۰** | ۱۲ms | **۱۰۰ms** | ۲۵۰ms | ۶۴۲ms |
| ورود هم‌زمان ۵۰۰۰ نفر + آپلود ۵۰۰۰ رزومه (۲۰۰ ثانیه‌ی اول) | ۷۶,۳۹۵ | **۰** | ۶۲۰ms | ۶.۱s | — | ۱۱.۴s |

- هر **۵۰۰۰ ورود و ۵۰۰۰ آپلود رزومه موفق** بودند.
- در اوج، هر نسخه‌ی بک‌اند فقط ۴۰٪ تا ۶۵٪ یک هسته را مصرف می‌کرد (ظرفیت آزاد).

### دور ۱ — سناریوی استرس (۱ تا ۵ ثانیه بین کلیک‌ها، ۳ برابر درخواست بیشتر) ❌ زمان پاسخ

| درخواست‌ها | خطا / 502 / 504 | میانه | صدک ۹۵ | بیشینه | بیشترین توان |
|---|---|---|---|---|---|
| ۱۸۷,۱۹۷ | **۰** | ۷.۷s | ۲۰s | ۳۳s | ~۵۰۰ درخواست/ثانیه |

این مدل (هر کاربر هر ۳ ثانیه یک کلیک، ۱۰ دقیقه پشت‌سرهم) حدود ۱۶۰۰ درخواست در ثانیه می‌خواهد —
بیش از ۳ برابر ظرفیت یک لپ‌تاپ. درخواست‌ها در صف ماندند ولی **حتی یکی هم با خطا یا 502/504 رد نشد**.

## جمع‌بندی معیارهای پذیرش

| معیار | نتیجه |
|---|---|
| زمان پاسخ زیر ۲ ثانیه در اوج ۵۰۰۰ کاربر هم‌زمان | ✅ صدک ۹۵ = **۱۰۰ms** (رفتار واقعی کاربر) |
| بدون کرش و بدون 502/504 تحت فشار بالا | ✅ **صفر** خطا در هر دو دور (بیش از ۴۴۰ هزار درخواست) |

## یافته‌ها و بهبودهایی که بر اساس اندازه‌گیری انجام شد

| یافته | اثر | اصلاح |
|---|---|---|
| Bcrypt (~۲۰۰ms CPU) داخل حلقه‌ی async اجرا می‌شد | هر ورود، کل سرور را برای همه قفل می‌کرد | اجرا در Thread Pool — ۸ ورود هم‌زمان ۵.۵ برابر سریع‌تر (`app/core/security.py`) |
| ورود با ایمیل ناموجود سریع‌تر پاسخ می‌داد | امکان حدس ایمیل‌های ثبت‌شده (Timing Attack) | زمان پاسخ یکسان برای ایمیل ناموجود |
| هر صفحه‌ی لیست ۳ کوئری می‌زد | فشار CPU بک‌اند و دیتابیس | صفحه‌ی اول: ۱ کوئری با نتیجه‌ی دقیقاً یکسان (`app/core/pagination.py`) |
| commit بی‌مورد در مسیرهای فقط‌خواندنی پورتال کارجو | یک رفت‌وبرگشت اضافه به دیتابیس در هر درخواست | حذف (`app/core/candidate_utils.py`) |
| لاگ تکراری uvicorn (Nginx همان را ثبت می‌کند) | CPU هدررفته زیر بار | `--no-access-log` |
| سقف ۱۰۲۴ اتصال Nginx | با ۵۰۰۰ کاربر به خطای 502 می‌رسید | ۱۶۳۸۴ اتصال (`frontend/nginx.main.conf`) |
| نوشتن فایل/آپلود S3 همگام | قفل شدن سرور حین آپلود | اجرا در Thread Pool (`app/core/storage.py`) |

## محدودیت شناخته‌شده و توصیه

**ورود هم‌زمان هزاران نفر** تنها نقطه‌ی فشار باقی‌مانده است: Bcrypt عمداً کند است (امنیت رمزها) و هر ورود
~۲۰۰ms CPU می‌گیرد؛ ورود ۲۵ نفر در ثانیه به‌تنهایی ~۵ هسته را مشغول می‌کند. توصیه برای Production:
- بک‌اند روی سرور(های) جدا از دیتابیس/Worker، با تعداد نسخه‌ی متناسب با هسته‌ها (`--scale backend_api=N`).
- کاهش دور Bcrypt **توصیه نمی‌شود** (امنیت رمزها فدای سرعت می‌شود).
